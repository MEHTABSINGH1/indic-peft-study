# How Much Does LoRA Lose? Parameter-Efficient Adaptation of Multilingual Encoders for Low-Resource Indic Languages

**Mehtab Singh** · M.Tech Data Science & AI, IIIT Dharwad

> **Status:** all 204 runs (main, rank ablation, data-size ablation) are finished. The numbers below come from `results/summary.json` and `results/RESULTS.md`, which are generated by `scripts/aggregate.py`.

## TL;DR

On SIB-200 topic classification for **Punjabi, Hindi, Kannada and Urdu**, LoRA trains **0.11%** of the parameters and uses **2.0× less GPU memory** than full fine-tuning (best encoder, IndicBERT-v2). Its macro-F1 is **0.5 points** below full fine-tuning on average over the four languages, and no per-language difference is significant for this encoder. Zero-shot transfer **Hindi → Punjabi** is **0.05 points** better than **English → Punjabi**, which is no real difference. **Hindi → Urdu** (the same spoken language in a different script) loses **1.5 points** against Hindi → Hindi, so the cost of a script change is small here. LoRA is less stable than full fine-tuning: some seeds fail to train (see Key findings).

## 1. Motivation

Most Indian languages have only a few hundred labelled examples for any given task. Full fine-tuning of every weight is expensive and can overfit at this scale. Parameter-efficient fine-tuning (PEFT) is cheap, but most results for it come from English or high-resource benchmarks. This project measures, under controlled conditions, **how much accuracy PEFT gives up, and when, for low-resource Indic languages**.

## 2. Research questions

| | Question | Experiment |
|---|---|---|
| **RQ1** | How close does LoRA get to full fine-tuning on Indic languages, and does the gap differ between Indic-specific (MuRIL, IndicBERT-v2) and general multilingual (XLM-R) encoders? | `configs/main.yaml` |
| **RQ2** | How do LoRA rank, target modules and the amount of labelled data affect the gap? | `configs/ablation_rank.yaml`, `configs/ablation_size.yaml` |
| **RQ3** | Which source language transfers best zero-shot to Punjabi, and how much does a script change alone cost (Hindi → Urdu)? | transfer matrix from `main.yaml` |
| **RQ4** *(optional)* | Does a 2B decoder LLM (Gemma-2-2B) with 4-bit QLoRA beat 237M-parameter Indic encoders? | `configs/llm_qlora.yaml` |

## 3. Setup

**Data: [SIB-200](https://huggingface.co/datasets/Davlan/sib200)** (Adelani et al., 2024). It has 7 topic classes and 701 / 99 / 204 train / dev / test sentences per language. The benchmark is **sentence-parallel**: every language has the same sentences, so score differences across languages come from the language and script, not from different data.

| Code | Language | Script |
|---|---|---|
| `pa` | Punjabi | Gurmukhi |
| `hi` | Hindi | Devanagari |
| `kn` | Kannada | Kannada |
| `ur` | Urdu | Perso-Arabic |
| `en` | English | Latin (transfer source only) |

**Models:** MuRIL-base, IndicBERT-v2 (MLM-only), XLM-RoBERTa-base and, optionally, Gemma-2-2B.

**Methods:** full fine-tuning, LoRA (r = 8 on query/value by default) and QLoRA (4-bit NF4 with double quantization).

**Classification head:** mean-pooled token states → dropout → linear layer, for every model and method (decoders use the last token). We do not use the checkpoint's `[CLS]` pooler: for MuRIL its output is almost identical for every sentence (mean pairwise cosine 0.999), so a freshly initialised head collapsed to the majority class (macro-F1 0.057). With a frozen encoder, a linear probe on mean-pooled features reaches 0.78 macro-F1 on Punjabi, compared with 0.74 on standardised pooler features.

**Protocol:**
- 10 epochs, with the best checkpoint chosen on dev macro-F1.
- Learning rate 5e-5 for full fine-tuning and 2e-3 for LoRA, with 10% warm-up. Both rates were chosen on the Punjabi **dev** set (seed 0, 10 epochs) from LoRA {5e-4, 1e-3, 2e-3, 3e-3} and full {2e-5, 3e-5, 5e-5, 1e-4}; see section 3.1.
- Max length 128 and batch size 16.
- **3 seeds** per configuration; results are reported as mean ± std.
- Significance of LoRA − full is tested with a **paired bootstrap** over test sentences (2,000 resamples, seeds pooled).
- Peak GPU memory is measured with `torch.cuda.max_memory_allocated`.

### 3.1 Learning-rate selection

MuRIL-base, Punjabi, seed 0, 10 epochs. Selection used the dev set only (99 sentences); test scores were not used. Rule: highest dev macro-F1, and if two rates are within 0.01, take the smaller one. Raw runs are in [`results/lrsearch/`](results/lrsearch/).

| Method | LR | Best dev macro-F1 | Best epoch |
|---|---|---|---|
| LoRA | 5e-4 | 0.7133 | 10 |
| LoRA | 1e-3 | 0.8061 | 7 |
| LoRA | **2e-3** | **0.8350** | 5 |
| LoRA | 3e-3 | 0.8326 | 7 |
| Full | 2e-5 | 0.8237 | 4 |
| Full | 3e-5 | 0.8503 | 9 |
| Full | **5e-5** | **0.8629** | 9 |
| Full | 1e-4 | 0.8308 | 10 |

For LoRA, 3e-3 is within 0.01 of 2e-3, so the smaller rate (2e-3) was chosen. This is a single-seed search on a small dev set, so differences of about 0.01 are within noise.

### Key findings

1. **LoRA is close to full fine-tuning for the best encoder.** For IndicBERT-v2, LoRA is 0.5 points below full fine-tuning on average over Punjabi, Hindi, Kannada and Urdu. The per-language differences range from −1.1 to +0.8 points, and none is significant (all p ≥ 0.37, Table 2). It trains 0.11% of the parameters and peaks at 2.25 GB instead of 4.51 GB, which is 2.0× less memory (not a much larger saving).
2. **LoRA is less stable across seeds.** Two cells show a significant gap: MuRIL on Kannada (−9.5 points, p = 0.001) and XLM-R on Urdu (−5.4, p = 0.001). In both, the large standard deviation (±14.3 in Table 1) comes from a single seed that did not train properly, not from a consistent loss. The LoRA learning rate was chosen on one seed of MuRIL/Punjabi, and it does not transfer safely to every model, language and seed. Full fine-tuning showed no such failures.
3. **Source language barely matters for zero-shot transfer.** In Table 3 (IndicBERT-v2, full fine-tuning), Hindi → Punjabi (85.8) equals English → Punjabi (85.8), a difference of 0.05 points. Hindi → Urdu is 85.3 against 86.8 for Hindi → Hindi, so the script change costs 1.5 points. Transfer is nearly flat across languages, which is plausible for a sentence-parallel benchmark with a shared multilingual encoder. These numbers are for one encoder; the other encoders' matrices are in `results/figures/`.
4. **The rank ablation did not isolate rank.** At low rank the macro-F1 values are within noise of each other (for example, attn_qv rank 1 gives 85.7 and rank 8 gives 84.9, Table 4). At rank 16 and above, many runs collapsed to chance level (attn_qv rank 64 gives 5.9 ± 0.4) because training diverged at the fixed learning rate of 2e-3. This is a learning-rate × rank interaction, so it is not evidence about adapter capacity. The nominal best setting (all-linear, rank 1: 86.1) is not meaningfully better than attn_qv rank 1.
5. **LoRA does not help when data is scarce; it hurts.** At 50 training examples LoRA is 10.3 points below full fine-tuning (average over Punjabi and Kannada, `summary.json`), and at 100 it is also well below (Table 5). From 200 examples upward the two are within noise, with LoRA slightly ahead at 200 in both languages. The common expectation that PEFT is better in the low-data regime was not supported at a single fixed learning rate.

## 5. Limitations

- SIB-200 is topic classification on short, formal FLORES sentences. The results may not hold for code-mixed or social-media text.
- There are 204 test sentences per language, so differences under about 2 points are often not significant. Table 2 shows which ones are.
- Hyper-parameters are fixed across languages rather than tuned per language. The learning rates were selected on one seed of MuRIL/Punjabi (section 3.1) and reused for every model, language, rank and data size, which is why some LoRA runs diverged.
- Training times in `results/RESULTS.md` are medians over runs and should be read as rough: the runs were done on a laptop GPU that was sometimes on battery power (clock-capped), and one run included a system sleep. Peak GPU memory and all F1 numbers are not affected.

## 6. Reproduce

```bash
pip install -r requirements.txt
pytest -q                                   # ~1 min on CPU
python scripts/sweep.py configs/smoke.yaml  # tiny CPU end-to-end run
python scripts/sweep.py configs/main.yaml           # GPU, ~2 h on a T4
python scripts/sweep.py configs/ablation_rank.yaml  # ~1 h
python scripts/sweep.py configs/ablation_size.yaml  # ~1 h
python scripts/aggregate.py
python scripts/error_analysis.py --model muril-base-cased --method full --train-lang hi --test-langs hi pa ur
```

There is also a one-click Colab notebook: [`notebooks/run_on_colab.ipynb`](notebooks/run_on_colab.ipynb). Runs are resumable, and finished configurations are skipped after a disconnect.

```
src/indicpeft/   data.py (SIB-200, stratified sub-sampling) · modeling.py (full / LoRA / QLoRA) · train.py (one run → JSON)
scripts/         sweep.py (YAML grid runner) · aggregate.py (tables, bootstrap, figures) · error_analysis.py
configs/         one YAML per experiment
results/runs/    one JSON per run, with raw predictions for re-analysis
```
